## Visual & game-feel

- ⭐ **Light shafts — TRIED AND REMOVED, and the thing that blocked it has now landed.** Its own note ended "or accepting that the effect needs the light-gated-visibility work" — that shipped, so a shaft is no longer decoration on an already-visible room: it would make the lit patch under a grate somewhere you can SEE from down the hall, and somewhere to stand or avoid standing.
  Retry notes from the first attempt: God-rays through a crypt grate or an arrow-slit. Built once (deterministic per-level placement from an integer hash, fed to `computeLightMap` as real `ExtraLight` sources, plus an additive pool on the overlay) and pulled: the idea reads, the execution didn't. Two dead ends already paid for, so don't repeat them:
  1. **Too dim.** The first tint (`#967a48`) was darker than `TORCH_EMBER`, the bare no-torch glow — among the faintest lights in the game, so it visibly lit nothing and hung in the air as a smudge. Any retry should sit near a lit torch (luma ~200). _Check a new light against the others in `lighting.ts` before blaming the rendering._
  2. **Cell background tints go blocky.** Tinting each cell across the pool made it visible as an unmistakable rectangle — a 3-tile falloff is only ~3 discrete steps and the grid shows straight through. Same failure the cracked-wall experiment documented; "it's an area, not an object" does not rescue it.
     What's left untried: shafts as an angled BEAM rather than a floor pool (a narrow parallelogram of light crossing the room, which reads as volume in a way a blob can't); tying them to actual map features (a real hole in a wall or roof placed at generation) so the light has a visible source instead of appearing from nowhere; and — now possible — placing them as real `GameMap` data the way sconces are, so the core lights by them and they can be authored per level.
- **Memory should decay** — explored tiles render at a fixed dim forever, so the map becomes a permanent record. **Light-gating raised the stakes**: `explored` now accumulates every distant lit room you ever glimpsed, so it grows much faster and records places you never actually walked. Fading them further with time-since-seen would make the map read as RECOLLECTION, and quietly encourage re-scouting. Needs a per-tile turn stamp (`explored` is a flat `number[]` today), so it is a real state change — but very on-theme for a realm going dark, and it pairs with the trail below.
- **Leave a trail** — faint fading footprints behind you, via the existing decal system. Best paired with memory decay: the one thing that stays vivid is where YOU have been.
- **Screen feedback** — a red vignette pulse when low-HP/poisoned, a white flash on a firebomb, subtle screen-shake (transform the layers, like the smooth-scroll already does).
- **Smooth AoE telegraphs** — a clean glowing circle/cone for a blast radius or an incoming attack, instead of blocky highlighted cells.
- **Minimap** — a tiny explored-tiles map in a HUD corner for the big levels.
- **Weather follow-ups** — fog that thickens/thins over a level; optional thunder SFX synced to the Ramparts lightning.

## Gameplay depth

_Light is core now (`state.visible` is the light-gated set), which makes a
cluster of things cheap that were previously impossible or merely cosmetic._

- ⭐ **Strike a light / snuff one out** — an action that lights or douses a wall sconce. `GameMap.sconces` is already a JSON-safe list of positions that roundtrips in the save, and `recomputeFOV` lights by it, so adding or removing an entry immediately changes what you can SEE — no new system at all. What it buys: a dark level you make navigable, a lit corridor you go dark to escape down, and a real cost to either (a turn, and being visible while you stand at the flame). The Antechamber's "the processional lights are failing" line already promises this.
- ⭐ **Something that EATS light** — the "pursuer you cannot kill" note below already proposes a hole in the light as its telegraph. That was cosmetic when light only coloured glyphs; now a negative light source would genuinely shrink `state.visible`, so the thing announcing itself and the thing being dangerous are the SAME mechanic — the dark it drags with it actually blinds you. Strongest version of that idea, and the cheapest to read.
- ⭐ **More light-EMITTING creatures.** A drifting distant light is the most-liked thing to come out of the lighting work, and it currently rests on one entry: `MonsterDef.glow`, set on the Will-o'-Wisp alone, on one level. The other three ambient species (raven, marsh frog, snow hare) are dark. It only started working when light moved into the core — before that a wisp beyond your torch radius was not in `state.visible` at all, so its glow could only ever light ground you could already see. Three directions, cheapest first:
  1. **More glowing species** — pure data (`glow` + an `ambient` `MonsterDef` + a `LevelConfig.ambient` entry). Cave moths around the Pit's glowcaps are the obvious one and are already listed under Content; the Pit is the level that teaches light, so a light that moves is on-message there.
  2. **A glow that is NOT harmless.** Every drifting light in the game is ambient wildlife you cannot fight, so light currently reads as a comfort. Something luminous and hostile inverts the read you just enjoyed — and it composes with the light-eater idea above, which does the opposite.
  3. **The folklore version** — a wisp that drifts AWAY as you approach, leading you off your route. Everything needed exists (`driftAmbient` and the shy radius); it is a change to which direction it flees, not new machinery. Pairs with the fact that the Blackwood is a `collectX` level where wandering has a real cost.
- **Monsters that shun or seek the light** — an AI trait keyed on the light map, which the core already computes once per turn in `recomputeFOV`. A ghoul that hugs the dark and a moth-like thing that beelines for your torch both fall out of one `MonsterDef` flag. Honest cost: the light map isn't currently handed to `actMonster`, so it needs stashing on the turn rather than recomputing per monster.
- **Torch fuel finally MEANS something — re-check the economy against that.** Running out used to be an inconvenience (you kept a room's worth of sight regardless); now it drops you to `CONFIG.unlitSight` of 3 indoors. That is the tension the light-gated work was for, but the shop stock and `fuel` values were tuned when it didn't bite. A balance question, deliberately not answered yet — flagged so it isn't discovered by a player instead.

- ⭐ **A pursuer you cannot kill** — something that enters a level and never stops: no HP, immune, always pathing to your last-seen tile. You survive it with TERRAIN — shut a door behind you, break LOS and let it lose you, put a chasm or water between you. Recommended first because it costs almost nothing new: `chase`, `lastSeen`, `loseInterestTurns`, `[c]` door-closing, `opensDoors` and knockback-into-void all exist and currently only matter at the margins; this makes every one of them load-bearing at once. It also fills a real gap — now that par is score-only, non-survive levels have no urgency at all, only attrition.
  - **Telegraphing it is the whole design problem**, and the rule is: the player must learn it WITHOUT PAYING for the lesson — one wasted turn, not a firebomb and half their HP. Four layers, each reusing a convention the game already taught: (1) a **non-letter glyph** (every monster is a letter, so this reads as "not a monster in the usual sense"), and better still make it a **hole in the light** — the lighting model multiplies glyphs by accumulated light, so an entity contributing NEGATIVE light darkens its own neighbourhood and says "the rules don't apply here" wordlessly; (2) the **HUD bar with a broken value** — `BossBar`/`EliteBars` already taught what a threat readout looks like, so the same furniture showing `∞` instead of a number is louder than a new widget; (3) **no damage number on the strike** — every hit floats one, so its absence is unmissable; (4) **one log line that also names the counter** ("…it does not bleed. Put a door between you."), because telling a player what fails is half a lesson.
  - **Needs a generator guarantee**: an escape must always exist (a door, a chokepoint, terrain to break LOS) — the same shape as `floodEscapeRoute` guaranteeing the flood can never seal you in. Without it, one bad seed turns this into a frustration engine.
- ⭐ **You hear what you can't see** (much stronger now) — a monster moving within some radius but OUTSIDE your FOV emits a log line (`· Something scrapes stone to the east.`) and a panned audio cue. Darkness is REAL now that sight is light-gated — but it is still pure penalty: you lose information and gain concealment. A second sense makes dousing your torch a real trade rather than a free win, and makes the dark atmospheric instead of empty. Uses the existing audio engine + the log-kind classifier; pairs with the `StereoPanner` note under Audio.
- ⭐ **Put your light down** (much stronger now) — drop or throw the torch. Light is CORE now, so a torch on the floor doesn't just render — it changes what you can SEE, and `GameMap.sconces` already proves the shape (a JSON-safe list of light positions that roundtrips in the save). What it buys is large: bait a lit room and watch from the dark, light the corridor you plan to retreat down, or go dark deliberately. Light stops being a stat you carry and becomes a thing you PLACE. (Complements the drop/discard action under Audio & UX.)
- ⭐ **Ice should DO something — and sliding beats slowing.** `ice` is mechanically inert today: outside generation it appears in exactly one place (`isWalkable`), plus the Rimewalk bridge that creates it. It is decoration on two levels — 25 tiles / 3% of the Frostspine (largest patch 15) and 7 tiles / 1% of the Ramparts.
  - The idea considered first was **difficult terrain** (2 turns to cross a tile). Rejected for a reason specific to this game rather than to the idea: **par is score-only**, so spending a turn costs nothing outside combat, and 25 of the 30 ice tiles sit on the Frostspine, a `killTarget` level with no clock. It would bite in exactly two places — mid-chase (the monster gets a free action) and the Ramparts, which is a survive level where turns ARE the goal, but that is 7 tiles. Worth remembering as a general filter: **a time cost is a weak lever in a game whose turn limit is only a score target.** Ice is also slippery rather than sticky; difficult terrain reads as mud.
  - **The slide**: step onto ice and keep going in that direction until a wall, a monster, or non-ice stops you. Better here because it is POSITIONAL, and position is still a real resource. It also lands in a level already built around **chasms and frozen tarns**, and reuses machinery that exists — `knockBack` already gates on `isWalkable` and gargoyle shoves into the void are already a death, so "slid into the crevasse" needs no new failure path. Hooks in beside `springTrap` / `brambleSnag` / `landFromLevitation` in `movePlayer`.
  - Knock-ons that make it richer, not harder: shoving a monster onto ice with the Flanged Mace slides IT (possibly into the void); a Rimewalk bridge becomes fast but un-stoppable-on; and Levitation, which already floats over water and chasms, is the clean counter.
  - Variant if the slide proves too swingy: keep the player sliding but make ice **slow for monsters**, turning an ice field into a defensive line you shoot across.
- **A throwable oil flask** — oil slicks catch fire and race, and firebombs exist, but oil is entirely level-authored: the player can never create it. A flask that makes your own slick to ignite turns fire from a hazard you route around into a tool you set up. Two existing systems, one new item.
- **More class abilities** — a second `[q]` ability per class, a charge/resource system, or ability upgrades bought in the shop.
- **Remaining weapon properties** — reach (hit 2 tiles), cleave (all adjacent), lifesteal, weapon-level crit. (Knockback / on-hit status / ranged already shipped; crit is currently the Rogue's trait.)
- **More boss mechanics** — build on Malachar's phased fight: barrage _lines/cones_, an add that must be killed to drop a shield, an enrage timer; maybe a mini-boss version of the pattern for Gorm / the Herald.

## Set-pieces & world richness

_Caveat: scale only feels epic if it's **populated** — match any size bump with density (monsters / forage / altars / secrets). Treat dynamic terrain as one-off set-pieces so the taut core isn't diluted._

- **The Pit oubliette** — a one-way trapdoor drop into a hidden loot pocket (a drop-tile that teleports you into a sealed cache with its own way out). The next level-design beat.
- ⭐ **Lightning should actually reveal** — the Ramparts storm already flashes the screen, but `paintLightning` is purely cosmetic, driven by the WALL CLOCK, and then MASKED to `state.visible` — so today a flash lights only what you can already see, which is the one thing it shouldn't do. Granting one turn of full visibility would convert an existing decoration into a mechanic and give the level a signature beat it currently lacks: you plan in the dark, then the sky shows you everything for a turn. Caveat: it has to move onto the turn clock and into `GameState` to stay deterministic and roundtrip in the save.
- **Vistas & scripted beats** — a distant landmark glimpsed through fog (Blackhall from the Pass), a portcullis grinding shut behind you, a collapsing bridge, a scripted ambush. Needs a small scripted-trigger hook (fire on reaching a tile / picking up an item / turn N); the distant-landmark one is render-heavy.
- **Secret-area follow-ups** — hidden rooms behind bump-to-reveal secret walls; lore fragments seeded inside vaults specifically (they currently draw from the region pool like any other prop).
- **Flood follow-ups** — a lever/altar-triggered flood, draining, or a second signature dynamic-terrain level.
- **A beat of calm** — a safe room / shrine alcove between horrors, so the danger lands harder by contrast.

## Design lessons (hard-won — keep in mind)

### Level design & placement

- ⭐ **"Farthest cell" is almost always a dead-end** — placing a quest item or boss at the strict maximum distance puts it at a corridor tip (measured: the Sunblade hit a 1-wide corridor on 7 of 8 seeds). It reads as the item plugging a passage, it's anticlimactic for a payoff item, and on a flooding level it's a death trap. `farthestCell` now trades a few tiles of distance for OPEN ground — but for QUEST ITEMS only. Applying it to bosses too dropped the Iron Gate 50%→17%: a corridor lets you fight a boss one-on-one while an open room lets its escort flank you, and a boss on a chokepoint is thematic anyway (the Gate Warden _holds the gate_). Generalizes twice over: when picking a spot by an extremum, check the SHAPE of what you get and not just the score — and the shape that's right for loot is wrong for a fight.
- ⭐ **A set-piece has to actually happen** — the crypt's flood started at turn 24 while runs finished around turn 43, so players saw ~2 of 7 steps: the level's whole identity was a coda. Tuning it to start early and span the hunt (with a thinner garrison so the water, not the horde, is the antagonist) raised exploration 37%→55%. Check that a signature mechanic overlaps the actual run length — `medTurns` vs the mechanic's schedule.
- ⭐ **Growing a level invalidates its whole tuning block** — `monsterBudget`, `forageCount`, `turnLimit` and (on flood levels) the flood timer are all calibrated against the OLD dimensions. Growing the Sunken Crypt 54×34 → 66×42 for a third region dropped its bot floor 50% → 17%. Two traps in the diagnosis: (1) `findItem` places its item at the FARTHEST cell, so a bigger map lengthens the hunt disproportionately — attrition, not the hazard, is what kills; (2) I assumed the flood was catching the player and retimed it, but deaths were at turn 23 with the flood starting at 32 — the hypothesis was simply wrong, and the fix that "worked" (60×38 + restored density) was a different change entirely. Re-measure after each single dial, and be suspicious when a fix lands without the metric that motivated it moving.
- **Match the GOAL to the map size** — a `killCount` cull completes wherever you happen to be fighting, so on a big map it ends in the spawn corner and the rest goes unseen; it also needs high density to stay winnable (which then makes traversal brutal). Big, varied maps want a goal that pulls you across them (`killTarget` placed farthest-from-start, `reachLocation`, scattered `collectX`). The Iron Gate moved cull → Gate Warden for exactly this, and its horde could then thin 18 → 13 (bot floor 33% → 50%, median turns up, end-HP down to 5 — it now fights the whole way).
- **Base-generator swaps hurt combat levels** — tight layouts (`rogue`/`uniform`, ~13–27% floor) leave no kiting room; navigation/collect goals tolerate them, combat goals don't. For combat-level variety, add a structural _wing_ on a forgiving digger base, or a purpose-built generator (the `hall`/`rampart`/`gallery` pattern), rather than swapping the base.
- **Per-seed variety needs real jitter** — a deterministic custom generator reads as "always the same." Add seed-driven structure changes (collapsed sections, optional transepts, varied/gated niches) like `genHall`/`genGallery` do.
- **Boss-keyed set-pieces need the right trigger** — HP-keyed effects only pay off on a long fight (the Throne dawn); on a level with a fast-dying gatekeeper, key off _approach distance_ instead (the Antechamber dusk), or the beat flashes by unseen.

### Readability (an unreadable glyph is a bug)

- ⭐ **"Sealed" must mean sealed to SIGHT, not just to movement** — the secret-vault enclosure check tested the 4 orthogonal neighbors, but FOV runs at `topology: 8`: one transparent diagonal corner let you see the entire vault (hoard, guardian and all) through the "sealed" wall, from 15+ tiles away. Structural containment and optical containment are different properties — whenever something is meant to be hidden, assert it against the FOV's own topology (test `[56]`), not against walkability.
- **A hazard and a boon must never share a glyph** — bramble and the altar both drew `‡`, separated only by color, so a thing that bleeds you looked like a thing that helps you. Bramble moved to `&` (ASCII, dense, tangled, not a letter so it can't read as a monster). Sharing a glyph across an item _category_ is fine and conventional (`!` for every potion); sharing one across opposite MEANINGS is the bug. `/style`'s collision report is the standing check — and it must read the RENDERED glyph (`terrainGlyph`), not the raw table, or it invents collisions that never reach the screen (it flagged `%` for crackedWall/forage, both of which are overridden before drawing).
- **Water is the game's thinnest color read** — measured across every hazard×terrain pair that can really co-occur, water is the bottom four: **121** on the Frostspine's grey-blue crags, then 161 (Blackwood trees), 165, 183. Everything else is ≥221. It survives on its `~` glyph plus the shimmer animation, but it's the one worth an art pass — a slightly deeper or greener blue on the mountain would lift the weakest pairing in the game. Test `[54]`'s floor sits just under it (110), so retinting water should come with tightening that bar.

### Testing discipline

- ⭐ **Pin a test's premise by PROPERTY, not by name.** `[40]`'s champions check asserted the `max(0.3, …)` elite floor using the Blackwood, "a level that declares no eliteChance" — true when written. Thinning garrisons and raising elite chances across the game gave the Blackwood one, and the check went red on a content edit that had broken nothing. It now finds such a level dynamically AND asserts one still exists, so if a future pass gives every level an eliteChance the floor becomes untestable and says so loudly instead of quietly passing. Same family as `levelIndexBy`: a premise stated as a name rots the moment content moves, and it fails in the confusing direction — the test looks broken, not the premise.

- ⭐ **An assertion must not be parameterized by the constant it means to pin.** The single most common flaw found, three separate times: `[23]` looped `CONFIG.crackedWallToughness - 1` times (at a dial of 1 that's ZERO bumps, so "withstands the first blows" was trivially true of an untouched wall); `[21]` asserted `hp === hp0 - CONFIG.eliteExplodeDamage` (at 0 that reads `hp === hp0`, passing on a blast that never happened); every assertion in `[31]` was relative to `CONFIG.parBonusMax`, so the whole section passed with the reward switched off. Such a test proves the code _reads_ the constant, never that the constant _does_ anything — **always pair it with an absolute anchor** (the dial is in a sane range / the effect is nonzero). Easy to reintroduce: a freshly written spawn-distance check had the same bug on its first draft.
- ⭐ **Formula coverage is not effect coverage.** Deleting `state.player.hp -= dmg` from `resolveMonsterAttack` — monsters dealing **no damage at all** — passed all three suites. The core tests exercised the damage _formula_ (`monsterAttackDamage`) and never the resolution path that applies it, and every playthrough gate is one-directional, so harmless monsters only made the bot win _more_. Test the wiring, not just the arithmetic.
- **Ask what ELSE could produce the state you're asserting.** "Striking a monster wakes it" passed with the alert line deleted, because the monster phase runs in the same turn and an adjacent visible monster wakes itself by _detection_. The fix is removing the other cause, not asserting harder.
  - **And a PROXY dies the moment the two things it conflated come apart.** The original fix asserted "the player can't see it" to mean "it can't detect the player" — identical statements only while the FOV radius WAS `lightRadius`. Light-gated sight split them: you keep a small unaided disc, so an adjacent monster now sits in `visible` while remaining unable to detect you (detection reads `player.lightRadius` directly and never touches `state.visible`). The check failed correctly, and the repair was to stop using a proxy at all — leave the target alone for a turn and assert BEHAVIOURALLY that it is still asleep. When a test asserts X to mean Y, write down which one you actually care about.
- ⭐ **Anything you rely on as a GUARANTEE must be asserted in core — balance gates erode.** This has now bitten twice. Teaching the bot to equip gear and use abilities made `minSpawnDistanceFromPlayer: 0` survive; widening the sweep from 6 seeds to 12 made "traps must have a bypass" survive, because the bot then won on one of the extra seeds and the beatable gate stopped firing. Balance gates are ONE-DIRECTIONAL — they only trip when the bot does badly — so every improvement to the bot or its sampling quietly erodes whatever they were incidentally covering. Note the trap rule was invisible to the trap-free-route checks too, because `ensureTrapsAvoidable` REPAIRS route violations after the fact: the route stays clean even when placement is broken, so the placement rule had to be asserted on its own terms. Re-run the mutation audit after touching the bot or its seed count, not just the suites.
- **Improving the bot can silently DELETE coverage.** Teaching it to equip upgrades and fire class abilities made `minSpawnDistanceFromPlayer: 0` survive a mutation `test:play` used to catch — a stronger bot simply clears the harder level. Keep _guarantees_ in verify-core where bot skill can't mask them; leave verify-play for _balance_.
- **A failing invariant may be a false positive in the CHECK, not a bug in the game.** The soak flagged the Frostspine's beast-den bear spawning at manhattan 5 on ~8 of 1000 seeds; the bear turned out to be sealed behind a non-walkable gate and dormant, unable to reach you at all. Verify the finding before relaxing the check _or_ patching the generator — the right fix was making the check mean "reachable by walking" rather than raw distance.
- ⭐ **A test named after a property is not evidence it checks that property — and removing one confound can introduce its mirror image.** `[S4]` is called "buy respects coins + maxQty" and mutation audit killed _both_ of those checks: the can't-afford assertion measured `bag.length` while the item under test was a STACKABLE potion (a successful buy bumps `count`, length never moves), and the cap assertion was confounded by funding of `price × maxQty + 5` so the PURSE refused the over-cap buy instead of the cap. Then fixing the funding made the entry sit at its cap, so the cap masked the purse — the same bug reflected. The escape is structural: for each gate, construct a case where **that gate is the only one that can fire** (here, an uncapped, unpurchased entry), and assert the quantity the operation actually changes.
- ⭐ **The measurement must not be shaped by the thing under test.** Two disguises of the same mistake, both hit while checking the lighting work. (1) A check that distant braziers no longer dim when you douse your torch excluded tiles within `lightRadius + 3` — but a lantern RAISES `lightRadius`, so the exclusion grew in the lit case and manufactured a difference (343 vs 402) out of nothing; a constant cutoff showed the truth. (2) Measuring sconce flicker by averaging over all sconce-lit tiles reported 2.6% and nearly got written up as "too weak" — each sconce runs on its own phase, so averaging ten of them CANCELS the flicker; measured one at a time they read ~12%. Before trusting a number, ask what it would read if the effect were absent, and whether any term in it moves with the variable.

- ⭐ **Measure the baseline AND the mutant before choosing a threshold.** Most generation properties are shares, not absolutes, and guessing the bar either passes vacuously or fails on legitimate output. Calibrating each one against a measured pair gave sharp, honest bars: quest-items-on-open-ground 86% intact vs 74% broken, forage-in-nooks 100% vs 0%, doors-on-chokepoints 99% vs 13%, flood-seed spread 11 vs 0. Because the seeds are fixed, those percentages are deterministic _values_ rather than samples, so a threshold between the pair is reliable. And several properties are legitimately **not** 100% — `farthestCell` falls back to the strict farthest cell when the far end has no open ground, and later passes convert a neighboring floor tile and retire a bridge or chokepoint after the fact.
- **Each placement pass defines its own "open neighbor" set — mirror the one you're testing.** `TRAP_OPEN` (floor/doorOpen/exit/oil/forage/ice) is _not_ what `placeCrackedWalls` or `placeDoors` use (floor/oil/exit/trap/trapSprung/doorOpen). Measuring cracked walls and doors with the wrong set produced two confident false failures. Relatedly: a shut `door` tile on a finished map is a secret-**vault gate**, not a failed `placeDoors` call, so "every door is generated open" is simply untrue of this game — the kind of thing only measuring first reveals.
- **Two traps specific to AI and probabilistic tests.** rot.js's first `getUniform()` after `setSeed(n)` is ≈ `n/2048`, so `new Rng(smallInt)` is not a fair coin — 80 fresh small seeds produced 80 _identical_ rolls; draw from one long-lived `Rng` or seed via `gameplaySeed(...)` (real gameplay is fine, its seeds are large hashes). And `stepToward` runs A* at **topology 4**, so a monster on a _diagonal_ ray from its target may legitimately stand still — align movement fixtures cardinally or you'll debug the pathfinder instead of the behavior.
- ⭐ **Read the DIAGONAL of a parameter sweep, not the whole grid.** Sweeping the Warrior's armour across all five tiers × every level looked alarming: **+31 mean win-rate points** from rags to plate, the Iron Gate going 10% → 93%, and **10 of 12 non-boss monsters floored to the min-1 damage** at plate (even the Gate Warden). Every one of those readings is OFF-DIAGONAL — plate at level 1, rags at level 9 — states the shop gates and no player reaches. Along the armour you would actually have on arrival, the curve reads 100 / 100 / 93 / 95 / 78 / 78 / 73 / 68 / 60: a clean ramp, tuned about right, needing nothing. The tell that the reading was wrong came before the correction and got ignored for a beat — the "obvious fix" (capping mitigation so armour never removes more than 60% of a hit) moved the mean by **one point**, because the steepness lives in the low-armour range where a cap cannot bite. A fix that does nothing is evidence the diagnosis is wrong, not that the fix was too timid. When a sweep spans states the game gates behind progression, most of the grid is counterfactual: find the path the player actually takes through it before concluding anything.
- ⭐ **Mutation-audit the suite periodically** — deliberately break real game code, one bug at a time, and see whether the suite turns red. Now a checked-in tool: `node scripts/mutation-audit.mjs` (78 mutations, ~5 min, deliberately outside `test:all`); add a row whenever you add a dial or a formula term. Cumulatively it has exposed **22 real holes**. Its `find` strings match LITERALLY, so a Prettier reflow can turn a mutation into a silent no-op — the runner reports those as `PATCH-MISSED`, and that line must never be ignored. The first audit scored 5 caught / 4 genuine holes: the **min-1 damage floor**, **DoT dealing 0 damage**, and the **sneak multiplier** were all documented load-bearing rules with no test, and the economy's wide 15–90% ratio rail happily absorbed a **4× coin inflation**. All four are now covered (`[53]` + a tuned-income band). Two lessons for running one: substitute ALL occurrences (a no-`/g` replace silently hits the wrong line and fakes a result), and expect **equivalent mutants** — `wardMitigate`'s floor looked like a survivor but is genuinely unobservable, since `mitigate` already guarantees `dmg ≥ 1`. A survivor needs diagnosing, not reflex-patching.
- **Verify the guard, not just the test** — after adding a safety net (`checkOver`, `levelIndexBy`), prove it actually FAILS on the case it guards (and exits non-zero) before trusting it. A guard that can't fail is worse than none: it looks like coverage. Both were confirmed end-to-end by temporarily breaking a premise and checking the exit code.
- **A test can pass while testing nothing** — three ways this has bitten: (1) `[].every(...)` is `true`, so an assertion over a collection a setup silently failed to build reports green having checked zero items (the Cleave test was one bad arena away from this) — use `checkOver`, which fails on an empty set; (2) mutating `LEVELS` at runtime from a test does NOT reach the engine — the test's module instance and the engine's are separate under tsx, so the override is invisible to `goalConfigFor` and the "test" verifies nothing. **This applies to `CONFIG` identically**, and cost real time to rediscover: three separate parameter sweeps (`sight`, `worldLightRange`) read perfectly flat because the script was mutating its own copy, and the giveaway was the suspiciously IDENTICAL output rather than any error. Sweep by editing the source file, the way the mutation audit does. Prefer real config + hand-built state over monkey-patching shared content; (3) a bare `LEVELS.findIndex(...)` for a test's premise silently yields -1 when content moves — use `levelIndexBy`, which names the lost premise and exits 1.
