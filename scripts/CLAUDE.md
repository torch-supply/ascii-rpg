# Test harnesses — methodology & per-check rationale

Deep-dive notes for `scripts/verify-*.mts` and `scripts/mutation-audit.mjs`. The root `CLAUDE.md`
says what each suite covers and how to run it; this file is the record of **why** each check is
asserted the way it is, and which traps to avoid when writing a new one.

## `verify-core.mts` — `npm run test:core`

- `[54] Color legibility` treats readability as a correctness property (it's an ASCII game — a glyph you can't pick out is a bug): the chasm's bg tint vs off-map black, status tints tellable apart, `@`/`>` popping against every terrain, floor-vs-wall separation, and a regression floor for hazards against terrain they can actually appear on. Thresholds are **measured, not guessed** (`colorDistance`, a redmean approximation in `tiles.ts`), and the scope is deliberately honest: color distance can't adjudicate every case — a trap reads fine at ~221 because its `^` carries the signal, while the old spore haze died at ~200 because a drifting mote has only color. Eyeballing is still required, which is what **`/style`** is for.
- `[53] Load-bearing invariants` exists because a **mutation audit** (break real game code, check the suite reddens) found them uncovered: the min-1 damage floor (without it an over-armored monster is unkillable and the fight can't resolve), poison/bleed/burn actually dealing damage, and the sneak bonus beating an alerted strike.
- `[0] Content integrity` runs FIRST by design: it sweeps every string id wiring content together (spawn/drop tables, structure + vault loot, shop tiers, monster loot, class kits, quest tags, ambient species) and every declared hex color. Those ids are invisible to the type system, and one typo otherwise surfaces as a raw stack trace from whichever later test happens to generate that level — or never, for ids generation doesn't touch (a bad `SHOP_TIERS` entry reaches the player, not the suite). Validating up front turns it into one line naming the exact offender.
- `[57] Tuning dials are load-bearing` is the output of a **systematic mutation audit** (46 mutations — neutralize a real formula term or config dial, then check the suites redden). It found **16 survivors**, of which 10 were true holes; closing them left 4, all verified **equivalent mutants** (the monster damage floor is redundantly enforced by `mitigate`'s own `Math.max(1, …)`; `levelParBonus`'s `Math.min(1, …)` is unreachable because the outer `Math.max(0, …)` handles over-par; `CONFIG.torchFuel` is a fallback both real torches override; `maxDecals: 0` doesn't stop recording, since `keys.length >= 0` deletes `decals[NaN]`). Re-run it with `node scripts/mutation-audit.mjs` whenever you add a dial or a formula term. The harness now carries **129 mutations across four passes** (`[57]` config/formulas, `[58]` `actions/index.ts`, `[59]` `generate.ts`, `[60]` inventory/state/altar/lighting/store) with **6 surviving — all verified equivalent**; a full run is ~9 min and is deliberately outside `test:all`. **Run `node scripts/mutation-audit.mjs --check` after touching any audited file** — it verifies every `find` anchor in seconds instead of surfacing a PATCH-MISSED nine minutes into a full run. That failure is easy to cause and invisible until then: reformatting `clonePlayer` to add one field silently turned its aliasing mutation into a no-op. It restores every file it touches, survives an interrupt (an on-disk recovery journal, because `execSync` blocks signal handlers) and refuses to run twice at once (a PID lock — two concurrent audits corrupt each other's edits).
  - **The dominant flaw it exposed, and the one to watch for: an assertion parameterized by the very constant it means to pin.** `[23]` looped `CONFIG.crackedWallToughness - 1` times, so at a dial of 1 it bashed ZERO times and "withstands the first blows" was trivially true of an untouched wall; `[21]` asserted `hp === hp0 - CONFIG.eliteExplodeDamage`, which at 0 reads `hp === hp0` and passes on a blast that never happened; every assertion in `[31]` was relative to `CONFIG.parBonusMax`, so the whole section passed with the reward switched off. These prove the code _reads_ the constant, never that the constant _does_ anything. **Pair every config-relative assertion with an absolute anchor** (the dial is in a sane range / the effect is nonzero). This is easy to reintroduce — the new spawn-distance check had the same bug on its first draft.
- `[58] Turn-resolution behavior` is the **second** audit pass — 32 mutations aimed squarely at `actions/index.ts` (2,365 lines of monster AI, the tick pipeline, kill rewards, hazard resolution), which the first pass had reached only indirectly through config dials. It found **12 uncovered behaviors**. The worst: deleting `state.player.hp -= dmg` from `resolveMonsterAttack` — monsters dealing **no damage at all** — passed all three suites, because every gate is one-directional (harmless monsters only make the bot win MORE, and "boss levels last ≥6 turns" passes _more_ easily) and the core tests exercised the damage FORMULA rather than the path that applies it. **Formula coverage is not effect coverage.** Also newly pinned: striking a monster wakes it (else every blow re-earns the sneak multiplier forever), the Rogue's crit, weapon `onHit` afflictions, knockback stopping at walls, bosses never giving up, last-seen pursuit, `slowChase` pacing, Emberstep vs. burn, and the lich's barrage actually landing.
  - **The confound trap, which is the AI-specific cousin of the self-referential one.** The monster phase runs in the SAME turn as your action, so an adjacent visible monster wakes itself by DETECTION — meaning "striking a monster wakes it" passed while the alert line was deleted, because something else set `chase`. The fix is to remove the other cause, not to assert harder: douse the light to 0 so `visible` holds only the player's tile, and `chase` can only have come from the blow. Whenever you assert that action X caused state Y, ask what _else_ in the same turn produces Y.
  - **Two more traps for anyone writing AI or probabilistic tests here.** (1) rot.js's first `getUniform()` after `setSeed(n)` is ≈ `n/2048`, so `new Rng(smallInt)` gives a near-deterministic first roll — 80 fresh small seeds produced 80 _identical_ crit outcomes. Draw from one long-lived `Rng`, or seed via `gameplaySeed(...)`. Real gameplay is unaffected (run seeds are large hashes, which spread fine). (2) `stepToward` runs A* at **topology 4**, so a monster placed on a _diagonal_ ray from its target may legitimately stand still — align movement fixtures cardinally or you'll debug the pathfinder instead of the behavior.
  - One survivor is a **deliberate** equivalent mutant, so don't "fix" it: the `p.lightRadius` term inside `detectRange`'s `Math.min` is redundant, because `computeVisible` already uses `lightRadius` as the FOV radius — so any monster in `visible` is within it by construction. Stealth is enforced structurally; the Shadowcloak term is the part that carries weight, and that one IS caught.
  - Also worth knowing: **`CONFIG` mutation does not reach `generate.ts` from inside these suites** (the same separate-module-instance quirk that once made a `LEVELS` mutation here verify nothing), so "flip a dial and re-generate" is not an available technique. Assert static bounds instead — e.g. placed forage ≤ `round(forageCount × forageScale)`, which is tight on half the levels.
- `[59] Generation placement rules` is the **third** audit pass — 23 mutations against `generate.ts` (1,992 lines, which the earlier passes had hit with only 4). It found **14 uncovered rules**, a 61% escape rate and the worst-covered file in the project: the soak checks generation's OUTPUT (reachability, connectivity) but nothing checked the placement rules themselves. Now pinned: quest items landing on OPEN ground rather than corridor stubs (the bug that once put the Sunblade in a 1-wide dead end on 7 of 8 seeds), no trap beside the player's start, spore-vent isolation, forage/lore preferring nooks off the beeline and staying off the doorstep, cracked walls bridging two spaces, doors sitting on 1-wide chokepoints, the flood's dilated dry spine + open doors conducting water + seeds spanning near→far, and a vault being a room rather than a slot.
  - **These are share-based thresholds, every one CALIBRATED against a measured baseline-vs-mutant pair** — e.g. quest-items-on-open-ground is 86% intact vs 74% with the preference disabled, forage-in-nooks 100% vs 0%, doors-on-chokepoints 99% vs 13%. Because the seeds are fixed, those percentages are deterministic _values_, not samples, so a threshold between the pair is a reliable discriminator rather than a flaky one. Several are deliberately **not** 100%: `farthestCell` falls back to the strict farthest cell when the far end has no open ground, and later placement passes convert a neighboring floor tile (to forage/altar/lore) which can retire a bridge or a chokepoint after the fact.
  - **Each placement pass defines its OWN "open neighbor" set** — `TRAP_OPEN` (floor/doorOpen/exit/oil/forage/ice) is not what `placeCrackedWalls` or `placeDoors` use (floor/oil/exit/trap/trapSprung/doorOpen). Measuring with the wrong one produced two confident false failures. Mirror the predicate of the pass you're testing, exactly.
  - Worth knowing before asserting anything about doors: a shut `door` tile on a finished map is a secret-**vault gate**, not a failed `placeDoors` call, so "every door is generated open" is a false statement about this game. Measured, not assumed.
- `[60] Inventory, snapshots & altar costs` is the **fourth** pass — 29 mutations across the last unaudited files (`inventory.ts`, `state.ts`, `altar.ts`, `lighting.ts`, `gameStore.ts`). It found **11 holes**, and the two worst were flaws in tests that _claimed_ to cover the thing. `[S4]` is literally named "buy respects coins + maxQty" and BOTH of those mutations survived it: its can't-afford assertion checked `bag.length`, but the shop's cheapest capped entry is a **potion, which stacks**, so a successful buy bumps `count` and leaves the length untouched; and its cap check was confounded by funding of `price × maxQty + 5`, so an over-cap purchase was refused by the PURSE, not the cap. Fixing the first confound then introduced its mirror image — reusing that same entry for the purse test meant the entry now sat at its cap, so the cap masked the purse. The working version uses an **uncapped, unpurchased** entry where the purse is the only possible gate.
  - The plain gaps it closed: equipping ARMOR discarded the old set (`[27]` only ever covered the weapon path), `giveItem` auto-equipping a WORSE weapon, ammo bundles yielding one arrow, `clonePlayer` aliasing the bag/effects, altars charging nothing (a spent one paying out twice; the hoard's blood price), and the par bonus never accruing on a clear.
  - The highest-stakes one: **`beginLevel`'s `entryPlayer` aliasing the live player.** That snapshot is what the store replays a level from after you die, so if it aliases, your restart inherits the damage and spent consumables that killed you — worthless in exactly the moment it exists for.
  - A **deliberate** equivalent mutant here too: a fuel-less torch counting as lit. `tickTorch` always clears `hasTorch` the moment fuel hits 0 and no item has `fuel: 0`, so `recomputeLight`'s `torchFuel > 0` term is unreachable defensive code.
- `[61] Camera / viewport math` is the renderer's only automated coverage. Most of `CanvasRenderer.ts` genuinely needs a canvas, but the camera is pure arithmetic and an off-by-one in either clamp is a **visible** bug — a dead strip along a map edge, or the player sliding off-centre — so `cameraOrigin` was extracted from `renderBase` as a pure export and `renderBase` now calls it (the test isn't asserting a copy). Verified against three mutations: an off-by-one bottom clamp, a missing origin clamp, and losing the centring.
- `[62] Hotbar slots are stable` pins the property the bag panel rests on: a number key means the same item all run. Verified against four mutations — index-based lookup, a `clonePlayer` alias, and two ways of releasing a claim. The **third** mutation is the instructive one: releasing stale claims inside `syncBagSlots` reddened only one check, because the new entry is pushed BEFORE sync runs, so its claim is never stale when examined — the honest mutation deletes the claim in `removeOneFromBag`, and that one reddens five. Note also that the re-acquisition check first empties slot 1 on purpose: without it, the rebought item's original slot happens to equal lowest-free and the check passes under a non-sticky implementation. **A test of "it went back where it was" is worthless unless "where it was" differs from where a naive rule would put it.**
- `[64] Log colour-coding` runs the log rail's classifier over lines lifted from the REAL message templates, because a heuristic over prose rots the moment someone rewords a message. It exists because the first version keyed on `/for \d+/` — which cannot tell "You strike the Skeleton for 8" from "The Skeleton hits you for 2", so **your own hits were painted as injuries**, on the most frequent line in the game. The rule is now grammatical: harm names YOU as the object, and numbers (which appear on both sides of an exchange) carry no weight. Two absolute anchors keep the mapping honest — every category must be reachable from a real message, and no two may share both a colour and a glyph — since without them the whole table could collapse into one category and still satisfy every individual assertion.
- `[65] Objective text says each number once` guards a split that only helps while it stays split: `goalTitle` is the countless objective the HUD row uses (its pips and "N of M" carry the figures), `goalLabel` adds them back for the intro card, which has no pips. Shipping them merged put the same count on screen three times. `goalLabel` is now DERIVED from `goalTitle` + `goalProgress` so the three can't drift, and the survive case is pinned both ways — the title defers its countdown to the HOLD gauge, the intro card still names the turns.
- `[66] HUD chrome legibility` is `[54]` for the DOM chrome, which had none. Components and test both read `hud/palette.ts`, so a tweak is measured rather than re-typed — the alternative (hex literals in both) is a test that passes while the chrome drifts under it. Two tiers on purpose: **text** must clear WCAG AA, **structure** (borders, dotted rules, empty-slot dashes) only has to register as present and is asserted to stay QUIETER than the secondary text, since holding a 1px rule to a reading bar is a false failure. It found two real defects on its first run: the footer key hints sat at **4.48**, a hair under AA, and my own gutter check was measuring the wrong thing — the map plate and the gutter differ by ~8, i.e. nothing, so the map's edge is carried entirely by its **border** (95–102). Asserting the fills would have been a threshold tuned to pass.
- `[63] The shop can't be farmed` asserts the RATIO no per-item price reveals: for every listing, sell-back value < purchase price. It exists because arrows were an **unbounded money loop** — buy a 12-arrow bundle for 8g, sell the arrows at 2g each for 24g, repeat (no `maxQty`). Every price involved looks reasonable in isolation; the bug lives only in the unit mismatch (`ItemDef.value` is a BUNDLE SIZE for ammo, but `sellBagItem` pays per unit), which is exactly the shape a per-item eyeball misses. The balance harness could never have caught it — the bot never sells. Paired with an absolute anchor (gear and potions still sell for something), because with an empty `SELLABLE` the ratio rule passes vacuously.
- Two harness guards keep tests from passing while verifying nothing: **`checkOver`** (use for any assertion over a runtime-built collection) FAILS on an empty set — `[].every()` is `true`, so a setup that silently produced nothing would otherwise report green; and **`levelIndexBy(label, pred)`** replaces bare `LEVELS.findIndex` for tests premised on a level existing — on a miss it exits 1 naming the lost premise instead of crashing on `LEVELS[-1]` (retiring the last `killCount` level broke two tests exactly that way).
- Both suites are **deterministic** — byte-identical output across repeat runs, so a diff is always a real change.

## `verify-playthrough.mts` — `npm run test:play`

- **The whole action surface is exercised in a live game.** The engine has 9 `PlayerAction` types: the bot emits 7 by autonomous choice, and `[P6]` drives the last two (`closeDoor`, `blinkTo`) against a real mid-run state — a live map with alerted monsters and fog — asserting they seal/teleport, spend the turn and the consumable, and **refuse without spending either** when illegal. They're injected rather than chosen because a bot heuristic costs more than it buys: a `closeDoor` heuristic **livelocks** (`PASSABLE` treats a shut door as passable, so the bot bumps to reopen the door it just closed — the loot-detour failure again), and `blinkTo` would mean adding a Phial to the loadout the table is calibrated on, perturbing every row for a niche consumable.
- Still not simulated, deliberately: detouring for loot, altars, and lore props (the latter two are covered end-to-end by `[S14]`/`[S10]` instead). The loot detour was **tried and measured twice** (separate pre-move step, then folded into the BFS goal set): both improved the metrics you'd want (whole-run purse 207g → 281g, `[P4]` best depth 4 → 9 with real spending) and both destabilized the harness — a run that never terminated, a 1914-turn death, the Antechamber 17% → 0%, and `[P5]`'s all-trials gate failing. The goal set is position-dependent, so the nearest-goal target flips turn to turn and livelocks; doing it properly needs a committed target with a detour budget. **Consequence for reading the table: `medGold` counts only what the bot trips over en route, so the economy figures are a LOWER bound.**
- The sweep runs **12 seeds**, not 6. Doubling costs +0.6s and halves the per-seed noise (8 points instead of 17), which matters because the floors below are only as sharp as the resolution — and it corrected readings that were wrong in BOTH directions: the Iron Gate showed 50% on 6 seeds and **25%** on 12 (the extra seeds were all deaths), while the Antechamber read 17% and is really 42%.
- **Per-level regression floors** (`WIN_FLOOR`) are the guard the aggregate gates couldn't be: "won ≥1 seed" plus a 30% overall rate would happily pass a level collapsing from 100% to 8%. That is not hypothetical — the Iron Gate quietly hit 17% and the Ramparts fell 50%→33%, both noticed only because a human read the table. Floors sit ~2–3 seeds BELOW the measured rate so they catch a collapse rather than a wobble; `throne_of_dusk` is deliberately absent (see `[P7]`). Update them intentionally when re-tuning — a floor lowered without thinking is how the regression this exists to catch gets waved through.
- `[P7]` answers the one question the table couldn't: **is the finale beatable?** `throne_of_dusk` reads 0% because every row plays a level in ISOLATION with a **fresh starting loadout** — so the bot fights an 80 HP lich holding the rusty dagger it starts the game with: 80 ÷ (3 power − 2 armor) = **80 melee hits**, versus 5 with the Sunblade it should have recovered from the Crypt one level earlier. That row measures a loadout no real player arrives with; it was never a balance verdict. Given the intended kit (Sunblade + plate + 4 heals + 6 firebombs — conservative, since the shops sell 16 bombs across the run at 20g against a ~215g purse) the bot clears it **63%** of seeds. A 2×2 isolates _why_, and both halves of the toolkit are asserted load-bearing:

  |              | 0 bombs | 6 bombs |
  | ------------ | ------- | ------- |
  | **dagger**   | 0%      | 13%     |
  | **Sunblade** | 0%      | **63%** |

  Bombs are necessary (0% without — the lich is dormant, so you soften it at range before it wakes) and the Sunblade multiplies 13% → 63%. That measures the design claim in this file, "beatable without the Sunblade only in theory."

- A caution learned the hard way: because a stronger bot clears more, **improving the bot can silently delete coverage**. Equip+ability made `minSpawnDistanceFromPlayer: 0` survive a mutation that `test:play` used to catch, so that guarantee moved into core (`[57]`) where bot skill can't mask it. Prefer core for any _guarantee_; leave `test:play` for _balance_.
- Prints a per-level difficulty table (win-rate / median turns / median end-HP / median gold-earned / **medSeen** = how much of the map a winning run explored, as `share%/absolute-tiles` / median death-turn) plus a **run-level economy** summary (whole-run purse vs. the cost of buying out every shop, asserted to stay in a 15–90% band so the shop remains a real choice — neither "buy everything" nor "afford nothing"). `medSeen` is a **design** metric (content in tiles nobody walks is content nobody sees) — but compare the ABSOLUTE tile count across levels, not the share: the share is skewed by how open a map is (the Great Hall is 77% floor, so it scores a low 21% while actually being walked farther than any level but the Blackwood). Within a level, the share is the useful figure — the win-rate is a conservative **floor** (greedy, non-optimal bot), so a low win% _with_ a low death-turn flags a meat-grinder; use the table to spot over/under-tuned levels. (The final lich stays ~0% — its multi-phase barrage/summon/blink fight is beyond a greedy bot, so that row is "not measurable here," not a balance verdict.)
- Every row plays levels in ISOLATION with a fresh, fully-stocked player, so `[P4]` adds **full-run continuity** — ONE carried character through the whole quest with real shopping and 3 lives (death restarts the level from the entry snapshot, as the store does). That's what exposes curve/economy effects the isolated table hides: `beginLevel` refills HP each level, so a carried run runs short of **consumables and gear money**, not HP — and the economy line above is an UPPER bound (it sums per-level medians as if all ten are cleared, whereas a real run banks far less). Its depth bar is a regression floor, not an ambition: the greedy bot spends its 3 lives on the first boss it can't out-trade, so ~3 levels is its natural ceiling.
- The table is a **Warrior** sweep; `[P3]` re-runs a reduced sweep as **every class** and holds each to the same "clears every navigation/attrition level" bar — Rogue and Pyromancer carry very different kits, so without it two-thirds of the classes would only ever be unit-tested in isolation.
- `[P5]` is the same idea for **run modifiers**, which the bot otherwise never opts into: core test `[52]` proves a mutated level still _generates_ legally, but "generates" isn't "survivable", so a trial that made a level unwinnable would ship green. The hard gate is only the WORST case (**all trials at once** still clears every navigation/attrition level on some seed, no invariant violated) — every trial is strictly a difficulty increase, so all-on subsumes the singles. **Do not read the single-trial rows as a difficulty ranking**: one run is 5 points at that sample size, and the bot is largely insensitive to what most trials change (it beelines, paths around traps, carries 3 heals), so `forsaken`/`champions` have both scored _above_ baseline — noise, not a finding. Guarded against vacuity by per-trial assertions that the mutated world is observably different at its own mechanism (drop the `mutators` arg and every row would silently collapse to baseline while both gates stayed green).

## `verify-store.mts` — `npm run test:store`

- **save fidelity** (a mid-run state with every recent field populated — drifting gas, lingering fire, decals, cracked-wall bash progress, known traps, quest progress, read-lore/spent-altar flags, flood step, active mutators — survives a quit→resume intact; plus a structural walker that rejects any live GameState value JSON can't carry, since a `Set`/`Map` degrades to `{}` on BOTH sides and would fool a naive equality check — this is what actually backs the docs' "JSON-safe → roundtrips in the save" claims, including for fields not yet written),
- the **trial-picker flow** (`[S13]`: `chooseClass` → `mutators` mode → `toggleMutator` on/off → `beginRun`, asserting the picks reach `GameState.mutators`, the chosen class survives the detour, and Glass really starts the run on one life). The mutator system was covered as config transforms (`[40]`/`[52]`), in real play (`[P5]`), and in the save (`[S12]`) — but the UI path turning a player's picks into a run was not, so a picker that dropped the selection would have shipped with all of those green.
- the **altar flow** (`[S14]`: step on → offer opens → decline costs nothing and leaves it unspent → accept changes the player and marks it spent → a spent altar never re-offers). The parallel lore modal had `[S10]` for ages, while the altar — which unlike lore _mutates the player_ — had never once had `acceptAltar` invoked by a test.
- the **targeting / overlay / preference surface** (`[S15]`): the cursor path that AIMS the throw and blink actions — `beginTargeting` → `moveCursor` (clamped to range) → `confirmTarget` (spends bomb + turn) / `cancelTarget` (spends neither) — plus a directional ability opening an aim where a bare tile-confirm cancels rather than firing blind, the pause/inventory/help overlays round-tripping, and the sound preference surviving a reboot. `[P6]` drives those actions as pure ACTIONS; nothing had exercised the UI that aims them.
- the **bag-hotkey surface** (`[S16]`): a number key routed through `handleCommand` quaffs its potion during live play (new behavior — the keys used to be inert unless the sheet was open), spends the turn, and opens no screen; a spent-but-reserved slot is inert and costs nothing; the panel's rows and the sheet's numbers agree; a click resolves identically; slots survive quit→resume. Verified against two store mutations — reverting the keys to inventory-only, and index-keyed lookup. The second is the one that names the bug: pressing the spent heal key **drank the antidote**.
- and **save compatibility** (a stale `contentVersion`, an unknown schema version, and corrupt/unparseable blobs each retire gracefully — Resume hidden, `resumeGame` bounces to the splash, boot never throws; this is the path every version bump relies on). Installs an in-memory `localStorage` shim (`sound`/`effectBus` self-guard to no-ops under Node).

## `verify-soak.mts` — `npm run test:soak`

- Also swept: **every trial plus the all-on stack** over a bounded slice of seeds (core `[52]` only covers a handful of fixed ones), and a **flood-softlock** probe that parks the player in the ADVERSARIAL spot — the floodable tile with the fewest walkable neighbors — then floods to maximum and asserts they can still walk to permanently-dry ground. That last detail is load-bearing: waiting on the protected spine is safe by construction, and even the farthest floodable tile only strands on 16% of seeds with the guard disabled, versus 42% for a dead end. The gentler versions passed with the escape guard deleted.
- It earned its keep immediately: at 1000 seeds it flagged the Frostspine's beast-den bear at manhattan 5 on ~8 seeds. That turned out to be a **false positive in the check, not a game bug** — a sealed vault `guardian` sits behind a non-walkable gate, dormant, and can't come to you, so the far-from-player rule rightly doesn't apply. The check now tests "reachable by WALKING" (no bashing cracked walls, no opening doors) rather than raw distance. Worth knowing before you "fix" a similar report.
