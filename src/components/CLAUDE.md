# HUD chrome & component internals

Detail for `src/components/**`. The root `CLAUDE.md` owns the cross-cutting rules — notably the
chrome-width trade-off (`LOG_RAIL_WIDTH` / `CHAR_PANEL_WIDTH` cost map columns) — and the rule that
React is a read-only consumer of store state.

## The death freeze-frame

Dying holds the last painted frame for `DEATH_FREEZE_MS` (1300ms, exported from the store so its input guard can share it) while the map drains to greyscale and dims, a red bloom fades over it, and the death card is withheld — then the card arrives. Two things about how it's built are load-bearing:

**The store transition stays SYNCHRONOUS.** `handleDeath` flips to `gameover`/`narration` on the lethal turn exactly as before, because `[S6]`/`[S7]` assert that and the LoopDriver shouldn't grow timing. The hold is purely view-layer: `handleDeath` bumps a presentation-only `deathFlash` counter, `GameRoot` watches it, keeps the canvas mounted past its usual `MODE_OVER_MAP` gate, and withholds the screen. Nothing about the death flow itself moved.

**Cancellation is DERIVED, not synced.** `frozen = freezing && !MODE_OVER_MAP[mode]` — so advancing early (the input-settle guard is only 250ms, so a player mashing Enter can outrun the freeze) drops the hold on the same render. On the LAST life the store arms its guard for the whole freeze instead (`[S7]`): game over has no "rise", and advancing from it quits to the title, so a skipped card is a lost run summary. The first draft used an effect calling `setFreezing(false)` on a mode change, which ESLint correctly flagged as a cascading render: an effect that setStates to reach a value an expression already knows is always a wasted render.

Skipped entirely under `prefers-reduced-motion` — no pause at all, which is the honest reading of the setting; the CSS block neutralises the animations as a second line of defence.

_Not done: highlighting the killer's glyph. `TurnResult`'s `damage` event carries the PLAYER's tile, not the attacker's, so the killer's position isn't available without threading it through the pure core._

## HUD chrome — four framed panels

The persistent chrome is four framed regions inside an 8px shell gutter with a 7px gap (`GameRoot`), each drawn by the shared **`hud/Frame.tsx`** (1px `#3a3a45` border + box-drawing corner glyphs sitting in the gutter). That frame is deliberately a DIFFERENT language from `ui/BoxFrame`, which the modals use — single slate rules here, double ember rules there, so a modal opening over the chrome reads as a distinct layer rather than more of the same.

- **`HudBar`** — two rows, split by what the information is ABOUT: **row 1 is the character** (class, a 15-cell `▰▱` vitality gauge, lives, gold — true wherever you are), **row 2 is the current level** (place, objective, and that objective's progress) plus **live status at its right edge**. That's the rule to keep when adding a field. Row 2 has a single **progress slot** that takes whichever form the goal needs — filled/hollow pips plus an "N of M" for a collect goal, the `SegGauge` countdown for a survive one — which is why the HOLD gauge sits beside "Hold out" rather than up in row 1, and why `SegGauge` survives for exactly that one case. The objective text uses **`goalTitle`** (see `[65]`), not `goalLabel`.
- **`LogRail`** (left of the map) — TWO TABS over one panel: the running message log, and a **Lore journal**. The tabs sit inside the existing panel rather than adding chrome, because the rail already costs map columns. The journal exists because `GameState.lore` is per-LEVEL — a fresh `beginLevel` discards it — so a fragment read two levels ago was simply gone, which is a poor deal for the one collectible whose entire payoff is its text. It reads `PlayerState.loreSeen` (titles, which carry across levels) and resolves prose through `loreByTitle`. Three ways that record can be silently lost, all pinned by `[74]`: `clonePlayer` must COPY the array rather than alias it (the `slotMap` bug — `entryPlayer` is a clone taken at level start); **`restartLevel` must carry it forward like `lives`**, since the journal records what you READ, not what you survived, and the level regenerates so a fragment found in a failed attempt would be unrecoverable; and titles must stay unique, because the index is keyed by title and a duplicate drops an entry. The log half is a vertical column of WRAPPING lines, as many as fit, scrolling back through the store's full retained history (`CONFIG.messageLogMax`). `flex-col-reverse` does double duty: it pins the newest line to the bottom AND makes the browser hold the scroll anchored there as messages arrive, so no scroll effect is needed. The top fade is a **mask on the viewport, not per-line opacity** — it has to stay pinned to the panel edge while you scroll, or it would drift away with its lines and leave a hard cut. Each line is a flex row with the glyph as its own child, giving a hanging indent so wrapped text aligns to the text edge rather than tucking under the icon. Keyed by absolute log position so the entry animation fires once per message, not per re-render.
- **`CharacterPanel`** (right of the map) — EQUIPPED · ABILITY · BAG(1-9).
- **Low HP pulses the gauge, and the RATE carries how bad it is.** Past the same 40% threshold that already turns it red, the vitality blocks and the HP figure pulse together as one unit — separately, the blocks throbbing beside a still number read as a glitch. The period eases from ~1.7s at the threshold to ~0.6s at death's door (`LOW_PULSE_SLOW`/`LOW_PULSE_FAST`), because colour alone can't distinguish 39% from 4% — red is red. Reuses the conditions' `statusPulse` keyframe, whose duration is now overridable per use via a `--pulse-ms` custom property, so there's still one alarm animation in the app.
- **Status sits in row 2, not the panel.** Conditions render as tinted, outlined, softly-pulsing alarm chips and buffs as compact glyph+count tokens, both at row 2's right edge. They lived at the bottom of the character panel first, which is the last place the eye goes and the furthest point from the `@` — a condition is the one status you must not miss, so it belongs where you already check HP. **Conditions never overflow**: past `CONDITION_DETAIL_MAX` the chips shed their `−N/turn` detail so they all still fit, rather than collapsing to a "+2" that says more exist without saying which — useless exactly when you're deciding whether to drink an antidote. Buffs may overflow; conditions may not.
- **`HudFooter`** — a 30px key strip holding the compact `SoundToggle`. The log leaving is what takes it from ~66px.

Two layout rules are load-bearing. **The rails are flex SIBLINGS of the map region, never overlays** — they must take real width so `GameCanvas`'s ResizeObserver narrows the viewport instead of the panel covering live map. And **the character panel never scrolls as a whole**: the BAG block takes the leftover height and scrolls internally, so CONDITIONS stay pinned and glanceable on a short window rather than sliding off the bottom.

## The bag panel & stable hotbar slots

The **BAG** block of `CharacterPanel` lists what each number key currently holds. It's a **legend, not a control surface**: keys `1-9` are bound globally in `keymap.ts` and now act during `playing` (previously they were inert unless the inventory sheet was open), so the panel is pure read-only chrome. Nothing in it is focusable — clicking routes to the same `useBagSlot` and `onMouseDown` preventDefaults, because focus parked on a row means the next arrow key re-fires it instead of moving the player. Slots are **stable for the run** (`PlayerState.slotMap`: item id → 1-9, JSON-safe, allocated in `core/hotbar.ts`). Keyed by DEF ID rather than stored on the `BagEntry` so a claim outlives its stack: run out of firebombs, rebuy them at the shop, they return to the same key. This is load-bearing, not polish — bag order is append-and-compact (`removeOneFromBag` splices), so anything index-derived **silently repoints the moment a stack empties**, which is precisely when you're watching your HP and not the panel. The concrete bug: quaff your last Healing Potion and `[1]` becomes the Greater Healing you were saving. A spent slot stays reserved and renders as a hole (`[2] —`) so the numbering stays readable; pressing it is inert and costs no turn. Claims are released only under pressure — when all 9 are taken and a new item needs one, the lowest claim whose item is **no longer carried** is evicted, so sold-off gear frees its key automatically. Overflow past 9 is sheet-only (the modal shows `[—]`), and **the sheet's rows are therefore a real control surface, not a legend** — the one place in the UI that differs from the panel. That was a genuine dead end for a while: the sheet was read-only (its only `onClick` closed it) and this panel renders a fixed `HOTBAR_SLOTS` rows, so a tenth distinct item had no key, no row and no route — it displayed as `[—]` and was carried, unusable, to the end of the run. Not a corner case: 13 item types can occupy a slot (the 13 potions — torches are FUEL, quest items go to `questProgress`, and arrows are skipped by `takesSlot` because their key could never do anything) against 9 keys, and 9 of the 13 potions are situational ones a careful player hoards, so eleven entries is an ordinary cautious bag. The fix is `store.useBagItem(defId)` — keyed by DEF ID precisely because a slotless entry has no slot to route by — with `useBagSlot(n)` now a thin resolve-then-delegate over it. Only ACTIONABLE rows become buttons; ammo, torches and quest items stay plain, since a button that does nothing is worse than a label. Store check `[S17]` pins it at both ends, and the second half is the point: every behavioural assertion drives the store directly, so reverting this row to a `<div>` would leave them all green while the item goes unreachable again — the same seam failure one level up — so `[S17]` also asserts, from the source, that the sheet still wires to `useBagItem`. The modal renders the SAME `slotMap` numbers; two numbering systems would be exactly the confusion this removes.

`hotbar.ts` is its own module for a mechanical reason: `inventory.ts` already imports `recomputeLight` from `state.ts`, and both need slot allocation (the bag is populated by acquisition AND from literals — the class kit, the dev jump, a resumed save), so putting it in either would cycle. `syncBagSlots` runs at those literal choke points plus `beginLevel` as a safety net. `clonePlayer` must copy `slotMap`, not alias it — the `entryPlayer` snapshot lesson from `[60]`.

**A readout's GLYPH must never be case-transformed.** The HP bars set `uppercase` on the whole label, which silently rewrote the glyph along with the name — and monster glyphs use both cases, with two pairs that actually collide: a snow hare's `h` displayed as `H`, which is **the Herald**, and a bat's `b` as `B`, the cave bear. These bars exist so you can match the readout to a thing on screen, so transforming the key you match on defeats them. The glyph now sits in its own `normal-case` span in both `BossBar` and `EliteBars`; core `[71]` pins the colliding pairs so the styling can't be "tidied" back.

**`GearModal`** — weighing a weapon or suit against the one you carry, opened by stepping onto it (`mode: "gear"`). It exists because you carry one of each, so picking a piece up puts down what you were using. Two details are load-bearing: it renders the **traits** (`onHit`/`knockback`/`ranged`) alongside the stat, because a bare power comparison is exactly the mistake the old auto-equip made — it discarded a Frostbrand's chill for one point of axe; and the comparison component is hoisted to module scope, since defining it inside the render creates a new component type every pass (ESLint catches this).

HUD overlays on the map region: `BossBar` (prominent HP bar shown while a boss — `isBoss` — is in `visible`), `EliteBars` (compact top-left HP bars for tough non-boss threats in view — champion elites and `MonsterDef.miniBoss` guards like the Gate Warden; capped at 4), and `LevelIntro` (a title+goal card that fades in when a level opens, then unmounts on a timer — it remounts because the canvas region unmounts during narration/shop).

## ASCII art

ASCII art (`AsciiArt`) supports flat color, CSS `gradient`, per-row `lineColors`, or per-region inline `{key}` `colors` tokens (tokens are zero-width → alignment safe); parents use `text-center`, so `.ascii` forces `text-align:left` to keep columns.

## Dev tooling & the `/style` gallery

**Dev tooling** (gated on `DEV = process.env.NODE_ENV !== "production"` in `src/lib/env.ts` — its own module so `/style` doesn't import the store, and with it the engine — so it's absent from the static build): the splash shows a **level picker** that jumps into any level with a tier-appropriate loadout (`store.debugJumpTo`), and in play `>` skips to the next level (`debugSkipLevel`). **`/style`** (`app/style/page.tsx` → `screens/StyleGallery.tsx`) is a dev-only **visual reference**, and the place to sanity-check anything visual. Sections: **tiles × biomes** as actually rendered; **POIs & overlays** (altar unspent/spent, lore inscription/remains/read, fire burning/guttering, gas, the barrage telegraph, a known-armed vs. sprung trap, `@`) — these are drawn OVER the grid and aren't `TileType`s, so they'd otherwise be invisible here; **lit vs. remembered** (fog ×`FOG_DIM`, since a color can read when lit yet vanish from memory); a **glyph-collision report** (one character meaning two things — it reads the RENDERED glyph via `terrainGlyph`, not the raw table, and labels deliberate collisions like floor/trap, wall/crackedWall and the per-CLASS item glyphs as intentional so a real one isn't buried). **Its input is the whole screen, not just terrain**: it compared only terrain against monsters for a long time, and so read clean while `∴` meant both a healing arcane mote and a cloud of poison, and `‼` for a wall sconce was two of the `!` that twelve potions share. Items, class badges, the player and every overlay are fed in now, and all three are fixed: the mote moved to `❖`, the sconce to `Ω`, and guttering fire to `▵`. What remains colliding is entirely WITHIN one category (twelve potions on `!`, seven weapons on `/`, the two quest items on `*` — which never coexist on a level), plus `✷` for the barrage vs. the Pyromancer badge, which is HUD chrome and never drawn on the map; biome palettes/ambients/atmospheres; monsters; class badges; items; **one monster under every tint it can wear** (species / elite / debuff); decals; weather; and the **activity log** — every message kind rendered on the real rail plate, with the AA ratio and colour distance beside it, plus each status affliction shown BOTH ways ("You are poisoned!" vs "The Skeleton is poisoned!") because that pair is the distinction the classifier most easily gets wrong. Its sample lines are lifted from the real message templates, not invented prose: the classifier is a heuristic over that text, so a made-up sample would prove nothing. Everything carries a live contrast reading (red &lt;110 / amber &lt;200 / green). It owns its own scroll container because `globals.css` sets `body { overflow: hidden }` for the game. It exists because the visual bugs that shipped were only ever caught by eye, late, after playing to the level that showed them; this makes that pass instant and systematic. Test `[54]` enforces the numeric floors, the gallery covers the judgement calls it can't.
